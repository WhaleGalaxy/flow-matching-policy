# 这个架构在 VLA 里的位置，以及本项目的测量对 VLA 设计说了什么

这份文档回答两个问题：**本项目的策略和 VLA 是什么关系**，
以及**项目里那些测量，对 VLA 的几个设计选择分别意味着什么**。

写它是因为 README 的"已知局限"里有一条：*架构仍然是 VLA 的形状而非 VLA*。
那句话是对的，但太短，它没说清楚差在哪一层、这个差别在本项目的任务上
到底会不会被观测到。

## 三种做法

把"看图 + 听指令 → 输出动作"这件事端到端做起来，目前有三条路线。

**一、动作离散成 token，由 VLM 自己解码。** RT-2、OpenVLA 一类。
动作的每一维分箱成若干离散 token，塞进语言模型的词表，于是"输出动作"和
"输出下一个词"是同一件事，视觉语言预训练的权重可以整个复用。
代价是动作的连续结构被分箱切碎，且自回归解码一次只出一步，
高频控制要靠动作分块或额外的解码技巧补回来。

**二、VLM 骨干 + 连续动作专家。** π0 一类。视觉语言骨干负责理解，
一个小的动作头（常用流匹配或扩散）负责生成动作块，两者之间用注意力连接。
动作保持连续，采样步数可以压到个位数，骨干的语义能力也保住了。
本项目的动作头就是这个形状。

**三、冻结的双塔编码器 + 动作头。** Diffusion Policy 一脉，也是**本项目**。
视觉一个骨干、语言一个骨干，各自独立预训练，在 token 层面拼接成条件，
送进动作头。

## 本项目为什么是第三种

不是因为第三种更好，是因为数据量和显存。

- **演示只有 1000 条/任务。** 微调一个 ViT 或一个 3B 的 VLM，在这个量级上必然过拟合。
  本项目冻结了 99.5% 的参数，只训 6.80M 的动作头。
- **8GB 显存。** 单是把 PaliGemma-3B 放进去做推理就已经吃满，
  再加训练的激活值放不下。可行的路子是冻结骨干 + 预计算特征缓存，
  本项目对 DINOv2 就是这么做的（数值等价，相对误差 2.2e-4，训练快 3 到 4 倍）。

所以第三种是这台机器上能做**受控对比**的唯一选择。而这个项目的主张是关于
动作头的（生成式还是回归、流匹配还是扩散），骨干只要三个方法共用同一个、
不构成混淆，就不影响结论。

## 差别到底在哪一层

双塔和单骨干的差别不在"有没有语言"，而在**语言和视觉有没有在骨干内部对齐**。

双塔拼接之后，"红色方块"这个短语和图像里那块红色区域，
在注意力看来是两个互不相干的 token，要靠动作头自己从 1000 条演示里学出对应关系。
单个视觉语言骨干在预训练阶段就已经把这件事做完了。

**但本项目的三个任务观测不到这个差别。** 原因说白了有点尴尬，值得写下来：

| 指令 | 场景里有几个候选物体 | 语言需要做的事 |
|---|---|---|
| Pick up the cube and move it to the goal position | 一个 | 选任务 |
| Push the cube to the goal region | 一个 | 选任务 |
| Stack the red cube on the green cube | 两个，颜色固定 | 选任务 |

三条指令的差别全在动词上，而 StackCube 虽然提到了颜色，
场景里也永远只有一块红的和一块绿的，不存在"哪一块"的歧义。
**也就是说，本项目的语言条件是任务选择，不是指代消解。**
一个 8 维的 one-hot 任务 ID 能达到同样的效果。

这不是说语言消融那张表是假的 —— 换掉指令 StackCube 从 32% 掉到 0%，
语言确实在承重。但它承的是"你现在该做哪个任务"这个重量，
不是"你说的是哪个物体"这个重量。VLA 真正的价值在后者，
而要观测到后者，任务集必须包含同一场景下多个候选物体的指代。
这是换骨干之前更该先换的东西。

## 项目的测量对 VLA 设计选择说了什么

四条，每条都有本项目的数字支撑，也都能直接迁移到上面第一、二种架构。

### 1. 条件怎么读进动作头，比动作头本身更重要

行为克隆基线原来把 83 个 context token 平均池化再过 MLP，
目标位置只占 1 个 token，被稀释成 1/83；换成与主方法逐层同构的 cross-attention
读出之后，同一个基线从 3% 到 52%。原先报告的 71 个百分点领先里，
**49 个来自读出方式，只有 23 个来自建模方式。**

对 VLA 的含义：π0 那一类"骨干 + 动作专家"的设计里，
真正承重的是动作专家**怎么注意到**骨干的输出，而不是动作专家用的是流匹配还是别的。
把条件压成一个池化向量再喂给动作头，是一种很容易写出来、
且不会报错的架构错误，它的代价可以达到数十个百分点。

### 2. 连续动作头会在离散自由度上给出物理上无意义的值

夹爪那一维在演示里几乎总在 ±1 附近，张开或闭合。
实测真实演示里 |g| < 0.5 的比例是 **0.0%**；而把两个都合法的动作块平均一下，
这个比例就变成 **49.5%** —— 一个悬在中间、既没夹住也没张开的指令。

对 VLA 的含义：这正是路线一（动作离散成 token）在夹爪这类自由度上的优势，
也是路线二需要单独处理它的理由。动作空间不是各维同质的，
把一个本质离散的自由度交给高斯流或 MSE 去建模，中间带就会被填上。
本项目没有对夹爪做特殊处理，这是一处明确可改的地方。

### 3. 流匹配相对扩散的少步优势是稳的，值得作为动作专家的默认选择

FM 回归的条件速度场是常数 `x₁ − x₀`，条件路径是直线，所以少步 Euler 积分就够。
实测 FM 两步 74%，同骨干同参数量的 DDPM 要 50 步才到 33%。
控制频率上限是 `execute_horizon / 推理延迟`，所以采样步数直接换算成可达控制频率。

对 VLA 的含义：动作专家选流匹配而不是扩散，这个选择在本项目上是站得住的，
而且理由是结构性的（路径是直线），不依赖具体任务。

### 4. 语言在目标视觉可见的任务上是冗余的

指令交换消融与观测充分性探针两个独立测量指向同一件事：

| 任务 | 目标在相机里可见（探针 R²） | 换成别的任务的指令 |
|---|---|---|
| PushCube | 可见（+0.99） | 94–100%，**不受影响** |
| PickCube | 不可见（≈0） | 62% → 8–26% |
| StackCube | 部分（+0.59/+0.51/−0.04） | 32% → 0% |

对 VLA 的含义：评测一个 VLA 的"语言能力"时，
必须先确认任务的关键信息**不能**从图像里直接恢复。
否则策略可以完全忽略指令而成功率不掉，而这在汇总表上看不出来。
这条对设计 benchmark 比对设计模型更有用。

## 换成单个视觉语言骨干，该怎么验证它有用

一个可证伪的问题，而不是"换上去看看涨不涨点"。

本项目的 PickCube 目标是每局随机的半透明标记，相机里不可见，
所以不得不把 3 维目标世界坐标硬塞进本体状态向量。接与不接是 6% 和 75%。
**这 3 维是一条绕过感知的旁路。**

于是问题是：换上视觉语言对齐的骨干之后，能不能把这条旁路砍掉。

- 能 → 对齐过的骨干提供了双塔拼接提供不了的东西，而且是在同一套受控协议下测出来的。
- 不能 → 也是一个有内容的负结果，说明瓶颈不在骨干的对齐，在目标物理上不可见。

要让这个实验有意义，任务集还得先补上真正需要指代消解的任务
（同一场景多个候选物体，指令指定其中一个）。这两件事的顺序不能颠倒：
**先有需要语言的任务，再谈需要更好的语言骨干。**
