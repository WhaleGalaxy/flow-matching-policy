# 调试记录：为什么第一版策略的成功率只有 4%

这份记录保留完整的排查过程。结论本身（换动作表示）不难，难的是从"loss 很低但机器人不动"
定位到根因，而这个过程恰恰是项目里最有价值的部分。

## 症状

第一次完整训练（FM，PickCube，20000 步，45 分钟）：

- 训练 loss 从 2.06 收敛到 **0.067**，曲线漂亮
- 成功率 **4.0%**，平均步长 294/300（几乎全部超时）
- **五次评测（4k/8k/12k/16k/20k 步）的成功率精确相等，都是 4.0%**

最后这一条是最重要的线索：如果策略输出真的在影响结果，成功率不可能完全不随训练变化。

## 排查过程

### 1. 环境配置：找到一个真 bug，但不是主因

演示数据的 `control_mode` 是 `pd_joint_pos`（绝对关节角），而 `gym.make` 的默认是
`pd_joint_delta_pos`（增量）。策略输出的绝对角度被当成增量、还被裁剪到 [-1,1]。

修复后成功率 2%（在噪声范围内），**没有解决问题**。教训：找到一个 bug 不等于找到了那个 bug。

现在 `make_env` 会显式指定控制模式并 assert 校验。

### 2. 分离"环境问题"与"策略问题"

把演示动作原样回放进评测环境：**10/10 成功**。环境是对的，问题在策略。

### 3. 观测分布是否一致

| | 均值 | 标准差 |
|---|---|---|
| 训练数据图像 | 123.0 | 48.1 |
| 评测环境图像 | 123.4 | 48.0 |

一致，排除渲染/预处理不匹配。

### 4. 视觉特征的空间精度（线性探针）

用冻结 DINOv2 的 patch token 线性回归方块位置：

| 输入分辨率 | patch 数 | x 误差 | y 误差 | R² |
|---|---|---|---|---|
| 98 | 49 | 10.1 mm | 13.3 mm | 0.94 / 0.89 |
| 126 | 81 | 8.8 mm | 9.6 mm | 0.96 / 0.94 |
| 182 | 169 | 7.6 mm | 7.8 mm | 0.96 / 0.96 |
| 224 | 256 | 6.8 mm | 6.7 mm | 0.97 / 0.97 |

方块边长 20mm。分辨率有帮助但收益递减 —— 原图本来就只有 128 像素，放大不增加信息。
这说明视觉特征**不是**主要瓶颈（位置信息在里面，精度也够粗定位）。

### 5. 看机器人实际在做什么

录制 rollout 并对比演示：

| | 演示 | 策略 |
|---|---|---|
| TCP 到方块距离 | 0.163 → **0.003** m | 0.163 → **0.22** m（越走越远） |
| 夹爪 | 接近时张开，到位才闭合 | **第 4 步就闭合**并保持 |

策略一上来就闭合夹爪并远离方块，随即进入演示中从未出现的状态（夹爪闭合 + 远离目标），
彻底脱离训练分布。

### 6. 根因：动作表示的信噪比

对每种控制模式，用**当前关节角**线性回归动作，看能解释多少动作方差：

| 动作表示 | 可由"手臂当前在哪"解释的方差 | 真正的任务信号 |
|---|---|---|
| `pd_joint_pos`（原始演示） | **98.4%** | **1.6%** |
| `pd_ee_delta_pose` | 36.1% | 63.9% |
| `pd_joint_delta_pos` | 34.0% | 66.0% |

**这就是根因。** 绝对关节角表示下，动作的 98.4% 只是在复述"手臂当前的构型"，
真正决定任务成败的信号只占 1.6%；而模型在动作块第 0 步的残差误差是 17%。
**噪声比信号大一个数量级**，再怎么调参也学不出可用策略。

这同时解释了为什么 loss 那么低还是不工作：模型确实把 93% 的动作方差拟合掉了，
但那 93% 里绝大部分是"手臂在哪"这种无用信息。**低 loss 完全可以来自拟合无关信号。**

## 修复

把演示重放转换到 `pd_ee_delta_pose`（末端位姿增量），这也是 ManiSkill3 官方图像
baseline 采用的模式。对视觉驱动的策略，末端空间还有额外好处：视觉特征直接给出
"方块在哪"，末端增量就是"朝那个方向移动多少"，不需要模型隐式地解逆运动学。

## 可复用的教训

1. **成功率完全不随训练步数变化 = 策略输出没被有效使用**，先查这条链路而不是调超参
2. **先把"环境对不对"和"策略对不对"分开**：把专家动作原样回放，一步定位
3. **生成模型的 loss 绝对值不能作为验收标准**，尤其当目标里混着大量易预测的无关成分
4. **动作表示的信噪比是模仿学习的一等公民**，应该在训练前就用线性探针量一下

# 第二轮：抓取率 95%，成功率 6%

换成 `pd_ee_delta_pose` 之后策略确实学会了任务的主体动作。20000 步的 FM，
在线权重，20 个 episode：

| 指标 | 数值 |
|---|---|
| 起始 TCP→方块距离 | 0.165 m |
| 最近 TCP→方块距离 | **0.016 m**（20 局里最差的一局也只有 0.052 m） |
| 抓到过方块 | **95%** |
| 成功率 | **6%**（100 episode 评测） |

也就是说：**看得见方块、够得着、抓得稳，然后放不对地方。**

## 不是训练不够

先排除最容易想到的解释。连续指标在 12000 / 16000 / 20000 步上是
dmin 0.025 → 0.022 → 0.016 m、抓取率 80% → 90% → 95%，确实还在改善，
所以"再多训一些"看起来合理。但抓取率已经接近天花板，而成功率几乎不动。

采样步数消融更直接：1 步 9%、2 步 3%、5 步 5%、10 步 6%。**采样质量根本
不影响结果** —— 如果瓶颈在"生成的动作不够精确"，加采样步数应当有效。

## 根因：目标位置不在观测里

用第 4 节同一套线性探针（冻结 DINOv2 patch token + 岭回归，n=300），
分别回归方块位置和目标位置：

| 回归目标 | x / y / z 误差 | R² | 该量本身的标准差 |
|---|---|---|---|
| 方块位置 | 9.4 / 16.2 mm | **0.96 / 0.88** | 59 / 59 mm |
| 目标位置 | 55.6 / 48.9 / 80.6 mm | **−0.14 / −0.23 / −0.12** | 59 / 58 / 87 mm |

方块那一行与第 4 节的结果吻合，说明探针本身有效。目标那一行的 R² **三个轴全是
负的**，误差与目标值自身的标准差几乎相等 —— 探针的预测还不如直接输出平均值。

**目标位置在 `base_camera` 的图像里不存在。** PickCube 每局随机目标（z 方向
跨度 0.024–0.311 m），而策略的输入只有 RGB 和 9 维关节角，`goal_pos` 从来
没有被接进去。策略一直被要求预测一个依赖于它无法观测的信息的动作。

## 这同时解释了基线的数字

目标不可观测时，给定观测的动作分布在目标位置上是**真正多模态**的 —— 演示里
同一幅图像对应着通往各个不同目标的轨迹。于是：

- **FM 采样其中一个模态**，在目标恰好接近该模态时成功 → 6%
- **BC 回归条件均值**，即"平均目标位置"，在目标接近工作空间中心时成功 → 4%

两个数字都不是偶然。这也是个反讽：README 用"BC 的 MSE 最优解是条件均值，
而均值往往是非法动作"来论证要用生成模型；这里 FM 确实正确地建模了多模态，
但当模态的成因是**信息缺失**而非任务本身的多解性时，正确采样一个模态并不能
提高成功率。生成模型解决不了观测里没有的东西。

## 修复

`obs/extra/goal_pos` 在环境和演示数据里都有，只是 dataset 只读了 `agent/qpos`。
`use_goal=true` 把它接进 proprio（9 → 12 维）：

```bash
python -m src.train ++use_goal=true
```

StackCube 和 PegInsertionSide 的 obs 里没有 `goal_pos` —— 它们的目标是场景里的
实物（另一个方块、插孔），原则上可见。这两个任务的困难另有来源：演示里带
`hand_camera`，而为了让多任务的观测空间统一，我们只用了 `base_camera`。

## 追加的教训

5. **训练前该检查的不只是动作表示，还有观测充分性**：任务的目标量能不能从观测
   里线性恢复？用同一套探针，几分钟就能答，比训练一轮便宜几个数量级。
6. **"高抓取率 + 低成功率"是观测缺失的典型指纹**：动作链条的前半段依赖可见信息
   （物体在哪）所以学得好，后半段依赖不可见信息（目标在哪）所以退化成猜测。
7. **消融的解释力受限于它依附的指标**：成功率在个位数时，采样步数消融画出来的
   是一条噪声曲线，看不出任何结论——不是消融设计错了，是先得把成功率拉起来。

## 第三轮：75% vs 4% 里有 71 个百分点不是建模方式（2026-09-11）

README 长期挂着这组数字：PickCube 单任务，同编码器、同 6.8M 参数、同 20000 步、
同样接了 `goal_pos`，Flow Matching 75%，等容量行为克隆 4%。

差距大到不正常。等容量 BC 不该只有 4% —— 演示数据是运动规划生成的，
同一个观测对应的动作分布并不宽，回归本来就该学得不错。

根因在**读出方式**，不在建模方式。BC 把 83 个 context token 平均池化再过 MLP，
而 `goal_pos` 只占 1 个 token，被稀释成 1/83；FM 走 cross-attention，
可以把注意力集中到那一个 token 上。于是这个对比同时改了两件事。

把 BC 换成与 FM 逐层同构的读出（同一个 `FMDenoiser` 骨干、同样的 cross-attention，
但没有噪声输入、没有流时间、一次前向直接回归动作块，参数量只多一个 query 的 112 个）：

| PickCube 单任务，其余条件完全相同 | 成功率 |
|---|---|
| Flow Matching（10 步采样） | 75% |
| **BC · cross-attention 读出（一次前向）** | **52%** |
| Diffusion Policy（100 步采样） | 33% |
| BC · 平均池化读出 | 3% |

**71 个百分点里有 49 个是读出方式，只有 23 个是建模方式。**
而且修好之后的 DDPM 基线在等预算下还不如一个读出方式正确的确定性回归。

教训与前两轮同构：一个大到需要解释的差距，先怀疑对比本身，
而不是先去解释它。`BCXAttnPolicy` 现在是仓库里的一等基线。

## 第四轮：DDPM 基线曾经是死的（2026-09-11）

指纹是**所有配置精确相等**：采样步数 1→50、执行长度 1→16，成功率全是 2.0%，
平均步长恒为 294.1。这个指纹在本文件里出现第三次了，每次都不是建模问题。

cosine 调度把 beta 上限 clamp 在 0.999，重新 cumprod 之后最后一项被压成
`alphas_cumprod[-1] ≈ 2.4e-7`，比前一项小 1000 倍（其余相邻步的比值都在 1–2 之间）。
而 DDIM 采样恰好从这一项起步：

    x0_pred = (x − √(1−ᾱ)·ε) / √ᾱ        1/√ᾱ ≈ 2029

噪声预测的误差被放大两千倍，下一步乘回 √ᾱ_prev 只抵消一部分，净放大约 31.6 倍，
采样值飞出去，动作被环境裁到边界，策略退化成常数输出。

裁剪 `x0_pred` 到 ±4（动作已归一化到单位方差，4σ 不会切掉真实动作）之后：

| DDPM 采样步数 | 1 | 2 | 4 | 8 | 16 | 50 | 100 |
|---|---|---|---|---|---|---|---|
| PickCube 成功率 | 2% | 2% | 3% | 10% | 25% | 33% | 33% |

这是 diffusers (`clip_sample=True`) 和 Diffusion Policy 的标准做法，不是调参。
修好之后这条曲线才有意义：DDPM 要 50 步才到 33%，而 FM 两步就有 74%。

## 第五轮：多任务塌成"只会做最容易的那个"（2026-09-11）

统一观测空间之后（`goal_slot`：13 维 = 关节角 9 + 目标 3 + 有效位 1，
没有 `goal_pos` 的任务填零并置 valid=0），三任务联合训练 20000 步：

| 任务 | PickCube | PushCube | StackCube |
|---|---|---|---|
| 成功率 | 3% | **82%** | 4% |

不是观测空间的问题了 —— 观测空间已经统一。也不只是预算问题：单任务 PickCube
在 8000 步就有 37%，而多任务给它的梯度步数是 20000/3 ≈ 6700，按预算稀释估计
应该在 20–30%，实测 3%，说明存在**任务间干扰**。

根因：任务身份全部落在语言 token 和本体/目标 token 上，而它们是 83 个 context
token 里的 2 个，只通过 cross-attention 被读取 —— 注意力完全可以不看它们。
于是策略学会了最容易的那个任务，然后到处执行它。

这正是 README 里"当前架构是 VLA 的形状，但两个模态只在 token 层面拼接"的实际代价。

## 第六轮：等条件 BC 打赢 FM，然后去量数据本身（2026-09-11/12）

多任务三任务、60000 步、同编码器同参数量同观测，100 episode：

| 方法 | PickCube | PushCube | StackCube |
|---|---|---|---|
| BC · cross-attention（一次前向） | **90%** | 94% | **48%** |
| Flow Matching（10 步采样） | 60% | **96%** | 36% |
| Diffusion Policy（100 步采样） | 44% | 92% | 3% |

FM 稳赢 DDPM（而且用十分之一的采样步数），但输给等条件的 BC。
在下结论之前依次排除了三件事。

**排除一：不是 CFG dropout 的不对称。** FM 和 DDPM 训练时有 20% 的样本指令被
替换成空串（为了兼学无条件速度场），BC 没有；而评测一律 `guidance=1.0`，
根本不走 CFG，所以这 20% 对 FM/DDPM 是纯粹的条件噪声。把它设成 0 之后
FM 从 63/90/7 变成 60/96/36 —— **确实有影响（StackCube 7%→36%），但不足以翻盘。**

**排除二：不是采样步数不够。** 2/4/10/20 步的 PickCube 成功率是 66/65/60/66%，
曲线是平的。少步积分误差不是瓶颈。

**排除三：不是 FM 过度发散。** 这一条需要量数据，不能靠猜。
`scripts/conditional_spread.py`：在真值状态空间（末端位置 + 被操作物位置 +
目标位置 + 夹爪开合）里找近邻，**近邻一律取自其它 episode**（同一条轨迹相邻
时刻的动作天然相似，算进来会把条件散度压到接近 0），量不同演示在同一情境下的
动作分歧，换算到动作归一化单位（边缘散度按定义为 1）：

| 任务 | 近邻半径 0–10mm | 10–20mm | 模型的采样散度 |
|---|---|---|---|
| PickCube | 0.40 | 0.40 | 0.325 |
| PushCube | 0.25 | 0.36 | — |
| StackCube | — | 0.33 | — |

**数据的条件散度 0.3–0.4，模型的采样散度 0.325 —— FM 校准良好，没有过度发散。**

### 真正的原因：散度是宽的单峰，不是多个模态

"MSE 回归的最优解是条件均值，而均值可能本身就是非法动作"这个选生成模型的理由，
依赖的**不是散度大，而是多模态**。散度区分不了"几个模态"和"一个宽的单峰"。

把每组近邻的动作块投到它们自己的主方向上，逐组标准化后攒起来看这个一维分布：

| 任务 | 主方向占方差 | 偏度 | 峰度 | 双峰系数 |
|---|---|---|---|---|
| PickCube | 62% | −0.03 | 2.02 | 0.494 |
| PushCube | 78% | +0.10 | 2.62 | 0.385 |
| StackCube | 62% | +0.16 | 2.12 | 0.484 |

双峰系数的正态参考值是 0.555，超过才提示双峰。三个任务全部低于它。
**这份数据的条件动作分布是一个宽的单峰**，条件均值本身就是合法动作 ——
于是生成式动作头没有任何多模态可以表示，而它为此付出的代价是实打实的。

这与另一条独立证据一致：**BC 输出的就是条件均值，它拿到 90%。**
如果分布真是双峰的，均值会落在两个模态之间，BC 应该失败才对。

### 一个被证伪的预测

顺着上面的诊断，可以推出：让 FM 采 K 个样本取平均（蒙特卡洛估计条件均值），
成功率应该向 BC 靠拢。实测：

| 采样数 K | PickCube | PushCube | StackCube |
|---|---|---|---|
| 1（实际推理用的） | 60% | 96% | 36% |
| 4 | 56% | 95% | 33% |
| 16 | 53% | 95% | 32% |

**不但没有帮助，还单调地变差。**

变差本身是有信息的：把 K 个样本平均，会把动作块里**时序位置不同**的事件抹平。
夹爪闭合是二值的，不同样本里闭合发生在第 5 步还是第 7 步，平均之后就变成
连续几步的中间值 —— 一个任何单个样本都不会产生、也不对应任何合法行为的动作块。
这说明那 0.3–0.4 的条件散度里有相当一部分是**时序上的相位差**，而不是幅值噪声。

所以差距不在"推理时抽样本而不是取均值"，而在**学到的条件均值本身**。

### 用开环误差把建模误差剥出来

成功率是闭环指标，把建模误差、积分误差和误差累积混在一起。
`scripts/action_accuracy.py` 只问一个开环问题：给定观测，预测的动作块离演示的
真实动作块有多远（PickCube，512 个观测，归一化动作单位，边缘标准差按定义为 1）：

| 方法 | 动作复现 RMSE | 占边缘 |
|---|---|---|
| FM 单样本（实际推理用的） | 0.284 | 28% |
| FM 16 样本均值 | 0.229 | 23% |
| **BC · cross-attention** | **0.154** | **15%** |

两件事同时成立：**采样确实注入误差**（取均值把 0.284 降到 0.229），
**但那不是主因** —— FM 用 16 个样本估计出来的条件均值，误差仍是 BC 的 1.5 倍。

于是根因是一句可以量化的话：

> **同等容量与预算下，去建模整个条件分布，代价是条件均值本身估得更差。**
> 而这份数据的条件分布是单峰的，条件均值就是需要的全部，
> 那份多出来的建模能力换不回任何东西。

这同时解释了为什么闭环里取均值反而更差：开环误差降了，但平均会把动作块里
**时序位置不同**的事件抹平（夹爪闭合是二值的），产生一个任何单个样本都不会
给出、也不对应任何合法行为的动作块。

### 这对项目主张意味着什么

原来的主张是"Flow Matching 相对确定性回归有实质增益"。数据不支持它，
但数据支持一个更有用的主张：

> 生成式动作头的收益取决于**演示数据的条件分布是不是多模态的**，
> 而这件事在训练之前就能量（`scripts/conditional_spread.py`，几分钟）。
> ManiSkill 的运动规划演示是单峰的，所以等条件的回归基线更强。

配套的实验是在同一个任务上制造真正的多模态：ManiSkill 对 PickCube 同时提供
`motionplanning` 和 `rl` 两套演示（后者是 PPO 学出来的另一套解法，
中位轨迹长度 50 步对 74 步），把两者混合即可，不改任务、不改观测、不改评测协议。

---

## 第七轮：容量更大、loss 更低、策略更差（2026-09-12）

第六轮定位到"同等容量下建模整个条件分布，代价是条件均值估得更差"。
顺着它有一个直接的补救：**给 FM 更多容量**。而且有交叉证据支持 ——
单任务（容量宽裕）FM 64% > BC 52%，三任务（容量摊薄）FM 在两个预算下都落后：

| 多任务三任务 | PickCube | PushCube | StackCube |
|---|---|---|---|
| FM 20000 步 | 12% | 83% | 2% |
| BC 20000 步 | 14% | 92% | 20% |
| FM 60000 步 | 60% | 96% | 36% |
| BC 60000 步 | 90% | 94% | 48% |

（这张表顺带否决了预算假设：BC 在两个预算下都赢，所以单任务与多任务方向相反
不是预算造成的，是**任务数**。）

把 FM 从 `d_model=256` 加宽到 `384`（6.80M → 15.01M，2.2 倍）：

| | 最终训练 loss | PickCube | PushCube | StackCube |
|---|---|---|---|---|
| FM 6.80M | 0.1147 | 60% | 96% | 36% |
| FM 15.01M | **0.1134** | **4%** | 95% | **8%** |

**loss 更低，策略崩掉。** 而且不是没训好：loss 曲线正常单调下降，
最终值比小模型更优。

机制与整条诊断链一致：容量更大 → 条件分布拟合得更忠实 → 采样时更忠实地复现
演示噪声 → 控制更差。**单峰数据上你要的是均值，而更好的生成模型给你的是更好的样本。**

仓库里原有一条"FM 的 loss 不会趋近 0，不能拿它当验收标准"。现在它有了更强的版本：
**FM 的 loss 与成功率可以反向移动。** 在这类项目里，loss 不只是"不够"，是可以误导。

## 第八轮：演示里记的是裁剪前的动作（2026-09-12）

为了检验"生成式动作头在多模态数据上更强"，把 PickCube 的运动规划演示与
PPO 演示混合（两种解法，中位轨迹 50 步对 74 步）。结果 FM 和 BC **双双掉到 3%**。

双双掉到 3% 是数据坏了的指纹，不是建模结果 —— 两个完全不同的方法不会
同时退化到同一个值。查动作统计：

| 来源 | 动作 std | 夹爪均值 | 越出 [−1,1] 的元素 |
|---|---|---|---|
| 运动规划 | [0.062 0.064 0.13 …] | +0.104 | **0.0%** |
| RL (PPO) | [0.25 0.248 0.54 …] | **−2.005** | **17.9%** |

夹爪均值 −2.0 越出了动作空间。根因：演示里记录的是策略的**原始输出**，
而环境执行前会把它裁到 [−1,1]。PPO 的输出是无界的（最大到 ±4.85），
运动规划的本来就落在范围内。合并归一化之后，运动规划的动作被压到 0.06 的尺度，
模型根本分辨不出来。

修法是数据集统一裁到 [−1,1]（对运动规划是空操作）。裁完之后数据性质也变了：

| PickCube 演示 | 条件散度 | 双峰系数（正态 0.555） | 判定 |
|---|---|---|---|
| 仅运动规划 | 0.42 | 0.494 | 单峰 |
| 仅 RL | 0.12 | 0.244 | 单峰 |
| 混合，**未**裁剪 | 1.03 | 0.721 | 看起来双峰 |
| 混合，已裁剪 | 1.05 | **0.547** | 宽的平顶单峰 |

**那个 0.721 有一部分是越界数值造成的假象。** 裁剪后卡在正态参考值边上，
峰度 1.89 ≈ 均匀分布。也就是说：混两种解法得到的是一个很宽、近乎平顶的单峰，
不是干净的双峰。

结论：**在 ManiSkill 上构造干净的多模态演示比预想的难。** 因此
"生成式动作头在多模态数据上更强"这条推论，本项目**没有**在实验上证实，
只证实了它的前提（多模态）在现有数据上不成立。这条要写进局限，
不能用一个半吊子的实验去暗示它。

## 这一轮的方法学教训

三条，都比具体的数字更可迁移：

1. **一个大到需要解释的差距，先怀疑对比本身。** 71 个百分点里 49 个是读出方式。
2. **"所有配置精确相等"和"两个不同方法退化到同一个值"都是实现坏了的指纹。**
   本项目各出现过三次和一次，没有一次是建模问题。
3. **凡是改变推理或观测的配置项，必须进结果表的 schema。**
   `use_goal` / `goal_slot` / `n_average` 漏记任一个，汇总脚本都会把不同实验
   平均成一个不对应任何实验的数字，而且不报错。踩过两次。

# 第九轮：列记下来了，汇总的时候却没用上（2026-09-12）

上一节的第 3 条教训是"凡是改变推理或观测的配置项，必须进结果表的 schema"。
这一轮发现那条教训只做了一半：**列确实加进了 CSV，但汇总脚本从来没读过它。**

## 症状：重跑汇总，头条数字对不上 README

改完留出集之后，拿现成的结果表跑一次 `make_report.py` 做回归检查：

```
| FM (Ours, multi-task) | 4±2% | 80±2% | 3±1% |
| BC · cross-attn       | 52±54% | 93±1% | 34±20% |
```

而 README 里那两行是 FM 60/96/36、BC 90/94/48。同一份 CSV、同一个脚本，
出来的表和已发布的结论**没有一个数字对得上**。

`52±54%` 这种读数本身就是指纹：标准差比均值还大，说明被平均到一起的根本不是
同一个量。

## 根因一：八个不同的实验共用一个方法名

`outputs/2026-09-11/multitask.csv` 里有 11 个 run。它们在这些维度上各不相同：

| run | 差在哪 | PickCube |
|---|---|---|
| `fm_mt_s42` | goal_slot 观测、20000 步 | 3% |
| `fmgc_mt_s42` | goal_slot + AdaLN 全局条件 | 6% |
| `fm_mt_tg_s42` | 每任务目标、20000 步 | 14% |
| `fm_mt_tg60_s42` | 每任务目标、60000 步、cfg_dropout=0.2 | 63% |
| `fmnocfg_mt_tg60_s42` | 同上但 cfg_dropout=0 | **60%**（README 那一行）|
| `fmot_mt_tg60_s42` | OT 耦合 + logit-normal 时间 | 2% |
| `fmwide_mt_tg60_s42` | d_model 384（15.01M） | 4% |
| `fmnocfg_mt_tg20_s42` | 20000 步 | 12% |

而 CSV 里能区分它们的列**一个都没有**：`task_goal`、`steps`、`d_model`、
`cfg_dropout`、`ot_coupling`、`global_cond` 全都不在表里。于是八行的 `model`
都是 `"fm"`、`multitask` 都是 `True`，被 `groupby(["method","task"])`
当成同一个方法的八个 seed，平均成 `4±2%`。

**它们的 `seed` 全都是 42。** 八个"seed 重复"里 seed 完全相同 —— 这件事表里看得见，
但没有任何代码去看它。

## 根因二：表里的名字把最后的线索也擦掉了

显示名是 `LABEL.get(m, LABEL.get(m.split("/")[0], m) + " · online")`：
只要方法串不在 `LABEL` 里就退回第一段。所以即便分组键修对了，
`fmwide`（4/95/8）和 `fmnocfg`（60/96/36）在表里仍然并排显示成两行
一模一样的 "FM (Ours) · online"。**读表的人没有任何办法知道哪行是哪个实验。**

## 根因三：`n_average` 记了，但同样没进分组键

`run_eval.py` 从第六轮起就把 `n_average` 写进 CSV 了，注释里还专门写了
"不记这一列，汇总脚本会把三者平均成 56%"。结果这一列从来没进过 `make_report`
的分组键，于是：

| ckpt | n_average | PickCube |
|---|---|---|
| `fmnocfg_mt_tg60_s42` | 1 | 60% |
| 同上 | 4 | 56% |
| 同上 | 16 | 53% |

三行被当成对同一个量的三次重复测量，平均成 56.3%。**注释里预言的那个数字，
一字不差地发生了。**

## 修复

三层，从"记下来"到"用上"到"记不下来时也别出错"：

1. **训练配置进 schema。** `run_eval.py` 的表头加上 `task_goal` / `val_frac` /
   `steps` / `d_model` / `cfg_dropout` / `ot_coupling` / `global_cond` / `sources`。
2. **汇总时按组内实际变化的列自动加后缀**（`make_report.variant_tags`）。
   只给**确实在变**的列加后缀，所以三个 seed 跑同一个配置时表格是干净的、
   `±std` 真的是种子间方差；一旦混进一个改了宽度或步数的 run，它立刻单独成行，
   并且后缀写明差在哪一维。`n_average` 与 `use_goal` 一并进了分组键，
   `n_average>1` 从主表里剔除（它和采样步数扫描一样是消融，不是主结果）。
3. **一条不需要任何额外信息的兜底判据**：同一个 method 下同一个 seed 出现在两个
   不同的 run 里，它们不可能是彼此的种子重复。撞上就用 run 名区分并打印警告。
   旧 CSV 已经丢掉的信息找不回来了，能做的是**不要安静地给出一个错的数**。
4. 显示名改成保留全部限定词（`make_report.label_of`）。

修完之后同一份 CSV 出来的表，`fmnocfg_mt_tg60_s42` 那一行是 60/96/36，
与 README 一致；`fmwide` 单独一行 4/95/8。四条都有回归测试钉住
（`tests/test_analysis.py`）。

## 顺带发现：三方对比里 cfg_dropout 没对齐

查 checkpoint 里存的 cfg 时发现的：

| run | cfg_dropout |
|---|---|
| `fmnocfg_mt_tg60_s42`（README 的 FM 行） | **0.0** |
| `ddpm_mt_tg60_s42`（README 的 Diffusion 行） | **0.2** |
| `bcx_mt_tg60_s42` | 不用这个旋钮 |

评测一律 `guidance=1.0`、不走 CFG，所以这个旋钮只在训练时起作用（20% 的样本
指令被置空）。但它确实是 FM 与 DDPM 之间一个没有对齐的变量，而"FM 稳赢
Diffusion"是本项目最有信心的一条结论。留出集那一轮重跑里三者统一 `cfg_dropout=0`。

## 教训

- **"进 schema"只是一半，另一半是"汇总时真的用上"。** 本项目在同一个坑里摔了
  三次：`use_goal`、`n_average`、训练配置。前两次的修法都是加一列，
  而加列并不会让下游去读它。
- **`52±54%` 这种读数要当成报错看。** 标准差大于均值，说明平均到一起的不是同一个量。
- **给聚合加一条不依赖 schema 的兜底判据。** "同一个 seed 不可能出现在两个 run 里"
  这句话不需要知道那两个 run 差在哪，就能拦住整类"信息没记下来"的错误。
- **显示名也是数据的一部分。** 把两行不同的实验显示成同一个名字，
  等于在最后一步把前面所有的区分工作作废。
