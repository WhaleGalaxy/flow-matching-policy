## 为什么要改计划

上一版计划的问题不在执行，在**主张**。当时这个仓库能拿出来的最好数字是
"PickCube 75%"和"推理快 9.3 倍"，两个都站不住：

- **PickCube 75% 说明不了什么。** PickCube 是 ManiSkill 的入门任务，
  纯状态输入的 RL 能做到接近 100%。面试官不会为这个数字停留。
- **9.3 倍不是发现，是算术。** FM 跑 10 步、DDPM 跑 100 步，同一个骨干，
  快 10 倍是定义决定的，不是测出来的。真正需要证明的是**DDPM 在 10 步下不行**，
  而这一点当时没有任何证据。
- **对比表是无效的。** 只有 FM 那一行看得见 `goal_pos`。这不是"结果偏乐观"，
  是这张表根本没有在比建模方式。

所以改的不是工作量，是这个项目在讲什么。

## 新的主张

> 在完全相同的骨干、参数量、训练预算和观测下，Flow Matching 用 **k 步**采样
> 达到 DDPM 需要 **m 步**才能达到的成功率；把实测延迟换算成机器人实际能跑的
> 闭环控制频率，两者的可行域差一个数量级。

这句话有三个好处：它是 Flow Matching 本来的卖点；它可以被证伪；而且证伪了也
仍然是个结果（"在这个任务尺度上 DDPM 少步也够用"同样值得写清楚）。

配套的第二条主线是**观测设计**，这条对具身岗位比建模更对口：

> 抓取率 95% 而成功率 6%，根因不在模型而在观测 —— 任务目标在相机里不可见。
> 这类问题有一个几分钟就能跑完的判据，不必先烧掉一轮训练。

## 执行清单

### 0. 修 bug ✅（已完成）

`scripts/diagnose_rollout.py` 自成一套 proprio 组装，遇到 `use_goal` 的
checkpoint 会崩。已改为调用 `src/data/dataset.py` 的 `build_proprio`。

### 1. 训练步数是否够 ✅（已完成）

同一批 checkpoint 用在线权重重测，100 episode：

| step | 4000 | 8000 | 12000 | 16000 | 20000 |
|---|---|---|---|---|---|
| 在线权重 | 6% | 37% | 59% | 70% | **75%** |
| 训练中途的 EMA 读数 | 8% | 4% | 4% | 4% | 4% |

两个结论：

1. **20000 步没收敛，但减速明显。** 所有方法统一用 20000 步，报成
   **等预算对比**而不是收敛对比，并在 README 里写明绝对数值被预算限制。
   这样也能和已经训好的 `fmgoal_PickCube_s42` 对齐，不用重训。
2. **EMA 读数在本项目里是坏的。** `decay=0.9999` 的时间常数是 10000 步，
   对 20000 步的训练太慢。上面两行是同一批权重 —— EMA 那行完全平的曲线会让人
   得出"训练没有进展"的相反结论。**评测一律 `--no-ema`。**

### 2. 受控对比（约 2.2 小时，🔄 进行中）

三个方法必须在**完全相同的观测配置**下训练：`use_goal=true`，20000 步，
PickCube 单任务。in-loop 评测关掉（EMA 读数无效，白花 30 分钟），
checkpoint 照存，最终数字离线用 `--no-ema` 出。

    python -m src.train model=bc ++model.hidden=2364 ++use_goal=true ...   # 等容量 6.81M
    python -m src.train model=ddpm ++use_goal=true ...
    python -m src.train ++use_goal=true ++seed=123 ...                      # FM 第二个 seed

误差棒：FM 两个 seed 是底线，基线单 seed，README 写明实测噪声 3 个百分点。

### 3. 主图：成功率 vs 可达闭环控制频率（核心交付）

复用 checkpoint，不重训。两个旋钮：

- **采样步数** n_steps：FM {1,2,4,8,16}，DDPM {1,2,4,8,16,50,100}
- **执行长度** execute_horizon：一次预测执行几步再重规划，{1,2,4,8,16}

横轴不是采样步数而是**机器人实际能跑多快**。推导：控制回路 f Hz、一次推理执行
H 步，则必须在 H/f 秒内算完下一块，所以可持续的最高控制频率是

    f_max = execute_horizon / 推理延迟

延迟由 `scripts/benchmark_inference.py` 实测。每个 (方法, 步数, 执行长度) 组合
给出一个 (f_max, 成功率) 点，取上包络就是这个方法的部署可行域。

这张图回答的是机器人岗位真正会问的问题：**给定我的控制频率要求，你的策略还能
用吗？** 而不是"你的模型 FLOPs 少多少"。

若 DDPM 在少步下并没有明显退化，如实呈现，并讨论为什么（动作块维度低、
任务相对简单、DDIM + cosine 调度本来就为少步优化过）。

### 4. 失败归因（复用 checkpoint）

PickCube 的动作链条是 接近 → 抓取 → 搬运 → 送达 → 静止。逐 episode 判定卡在
哪一段，画成堆叠柱状图，三个方法各一根。

这比一个成功率数字有用得多：它能区分"没学会看"和"学会了但抖"，
也是"抓取率 95% / 成功率 6%"那个结论的一般化形式。

### 5. 观测充分性探针 ✅（已完成，工具化）

`scripts/probe_observability.py`：冻结视觉特征 + 岭回归，在留出集上报 R²，
逐个物理量回答"这个量在观测里吗"。三个设计点缺一不可 —— 留出集报数、
基准用训练集均值（这样 R² 才可能为负）、正则强度在内层验证集上选
（否则欠正则的探针把什么都测成不可观测，负结论就没意义了）。

这是把项目里代价最高的一课变成了一个训练前几分钟就能跑的检查。

## 明确不做

- **PegInsertion 不救。** 只用 `base_camera`，缺腕部相机，原因清楚，
  投入几小时仍大概率难看。
- **多任务不重跑。** 当前 3/3/0% 的根因是可说清楚的：多任务要求统一观测空间，
  而 PickCube 的目标是不可见的随机标记（必须显式给 `goal_pos`），
  StackCube / PegInsertion 的目标是场景实物（obs 里根本没有 `goal_pos`）。
  **"统一观测空间"与"提供显式目标"在这三个任务上不可兼得** —— 这是个真实的
  设计冲突，写清楚比硬跑一轮 3% 有价值。解法（每任务一个目标编码头，
  或改用目标图像条件）写进 README 的下一步。
- **不做多 seed 的大规模扫描。** 把测量噪声写明更有说服力。

## 验收标准

做完之后，这个仓库应当能回答面试官的这几个问题而不心虚：

1. 你的方法比基线好在哪？—— 同等成功率下可达控制频率高一个数量级，
   有主图和延迟基准两条独立证据
2. 对比公平吗？—— 同编码器、同 denoiser 结构、同参数量、同训练预算、同观测配置
3. 你怎么知道差距不是噪声？—— 测量噪声实测 3 个百分点，且 FM 有两个 seed
4. 哪里没做成，为什么？—— 两个任务失败，根因定位到观测不足与一个具体的
   设计冲突，下一步明确
5. 你踩过最难的坑是什么？—— 动作表示信噪比、目标不可观测，
   都有量化证据、对照组，以及固化成脚本的判据
